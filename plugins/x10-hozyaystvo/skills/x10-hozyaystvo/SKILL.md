# Хозяйство x10

То, что верно у нас и не выводится из кода. Общие правила работы — как не
обмануться проверкой, ловушки оболочки и git, ведение работы — в соседнем
плагине `x10-obshchie@x10company`.

**Машинное сюда не кладём.** Пути к секретам, дерево каталогов, устройство
конкретной машины — у каждой машины своё, и живёт оно в её собственном месте:
у монорепо `automation/.claude/skills/`, у мака — репозиторий `mashina`.

## Где что работает

- **Hetzner, CentOS Stream 10** — ClickHouse, Grafana, Keitaro, Docker.
- **ERP на Laravel** — отдельный VPS Beget.
- **Cloudflare** — DNS, прокси, почта. **Bunny CDN** — видео и HLS.
- **GitHub, организация `x10company`** — без дефиса. Состав на 04.09.2026:
  публичные `ci-guard`, `claude-skills`; приватные `ApiX10`, `automation`,
  `GlobalBot_V2`, `loj`, `xray`.

**Список репозиториев не переписывать по памяти, сверять командой.** До
04.09.2026 в правилах на другой машине стояло «`x10-company`: erp, api,
bot-telegram, scripts, watchtower» — неверно целиком, ни одного из этих имён в
организации нет. Ошибка прожила месяцы, потому что её не с чем было сверить:

```bash
gh repo list x10company --limit 50
```

## Ловушки внешних систем

- **Facebook** — только system user tokens, `appsecret_proof` через HMAC-SHA256.
- **Airtable, linked record в формуле** возвращает строку через запятую, а не
  массив. Множественность проверять через `FIND(",", {field})`. Lookup приводить
  к строке через `"" &`.

## Границы рантаймов

Один и тот же `.js` в этом репозитории живёт в четырёх разных местах, и способ
достать секрет у каждого свой:

| Где исполняется | Как берётся секрет |
|---|---|
| node на этой машине | `process.env.X10_FOO` |
| Автоматизация Airtable | `input.secret('X10_FOO')` |
| Расширение Scripting в Airtable | `input.textAsync(...)` |
| Страница в браузере | `localStorage` |
| Апишка (C#) | `Environment.GetEnvironmentVariable("X10_FOO")` |

Промах: в `accounts-audit.html` попал `process.env`. В браузере это
`ReferenceError` при загрузке — страница не открывалась бы вовсе.

**Граница HTTP не видна ни одному графу вызовов.** Скрипт Airtable зовёт
контроллер не по имени класса, а по адресу:

```
[Route("api/[controller]")] + class SyncKeitaroOneCampaignController
    -> https://api.x10company.com/api/SyncKeitaroOneCampaign
```

ASP.NET отрезает суффикс `Controller`, поэтому поиск по имени класса зовущих
не находит: в JS этого имени нет. Проверено 19.08.2026 на индексаторе
codebase-memory-mcp — на вопрос «кто зовёт SyncKeitaroOneCampaign» он вернул
ноль зовущих.

**Апишка живёт в отдельном репозитории** `x10company/ApiX10` — с 03.09.2026.
Контроллеры там, зовущие их скрипты Airtable здесь. Поэтому вопрос «кто зовёт»
из одного дерева не решается, инструменту надо дать второй корень.

**Перед переименованием чего угодно, что зовут снаружи:**

```bash
python tools/kto-zovyot.py SyncKeitaroOneCampaignController \n    --takzhe "C:\Cursor Projects\ApiX10"
```

Он проходит правило маршрута в обе стороны и помечает, в каком рантайме
исполняется каждый нашедшийся файл. Если рантаймов больше одного —
выкладывать правки надо согласованно, иначе между выкладками апишка отвечает
404 живым скриптам.

## Три дома для значения

Правило заведено 23.08.2026, когда выяснилось, что один и тот же ключ Keitaro
жил в двух местах с разными значениями и никто не знал, какое рабочее.

| Что это | Где живёт | Как читать |
|---|---|---|
| Секрет: токен, пароль, приватный ключ | переменная `X10_*`, значение в `C:\secrets.env` | `os.environ["X10_FOO"]`; для файлов — путь в переменной |
| Адрес или идентификатор, нужный больше чем одному проекту: чаты, базы и таблицы Airtable, домен трекера, адрес сервера | `config/ids.json` | `from ids import IDS` |
| Настройка только этого проекта: режим работы, порт локального API, путь к профилю браузера | `.env` рядом с проектом | `dotenv` |

**Никакое значение не живёт в двух местах.** Дубль безобиден ровно до первой
ротации: сменишь ключ в одном месте, второе продолжит работать со старым, и
заметишь не в момент правки, а когда что-то тихо перестанет ходить.

Реестр читается из любой глубины подъёмом вверх — так, а не фиксированным
`..\..`, потому что точки чтения лежат на разной глубине:

```python
_d = os.path.dirname(os.path.abspath(__file__))
for _ in range(10):
    if os.path.isfile(os.path.join(_d, 'config', 'ids.py')):
        break
    _d = os.path.dirname(_d)
sys.path.insert(0, os.path.join(_d, 'config'))
from ids import IDS
```

Исключение — код, который исполняется не на этой машине: скрипты автоматизаций
Airtable, серверные `.sh`, приложения из `C:\Скрипты`. Файла реестра они не
видят, там значение остаётся зашитым — и тогда рядом с записью в реестре надо
пометить, где лежит вторая копия. Пометка — не бюрократия: она единственное,
что связывает копию с оригиналом при ротации.

Сторож проверяет это правило сам: `getenv("KEY", "значение")`, секрет в скрытом
игнором `.env`, приватный ключ в дереве — всё это находки, а не стиль.

## Keitaro и Airtable — только чтение

Любые чистки, удаления и изменения данных в этих двух системах — **только с
явного разрешения владельца, каждый раз отдельно**. Не «мы же договорились
в прошлый раз».

Причина в связке: Airtable управляет заливами, Keitaro крутит трафик, и
автоматизации гоняют данные между ними в обе стороны. Ошибка уезжает дальше
сама, а откатить нечем — истории по полю в Airtable нет.

Отсюда рабочий порядок:

- Читать свободно. `GET` в admin API, выгрузка записей, `diag.sh` — этим и
  надо пользоваться, чтобы отвечать фактами, а не догадками. Оговорка: Cloudflare
  перед трекером рубит клиенты без браузерного `User-Agent` — отдаёт **403 с
  телом `error code: 1010`**, и это выглядит как «ключ неверный». Скрипту нужен
  свой UA. Домены `keitaro.x10.fun` и `keitaro.x10company.com` ведут на один
  трекер, оба рабочие.
- Скрипт, который умеет писать, запускать **только сухим прогоном**, пока не
  сказано «пиши». Нет сухого прогона — сначала добавить его.
- Массовую запись без явно заданной области запрещать в самом скрипте.
  Так сделано в `keitaro/update-lp-fields.js`.

## Порядок на боевом

Сначала выяснить, кто фактически исполняет этот код, и проверить в настоящем
окружении, а не в похожем. Дальше — окно наблюдения и заранее готовый откат.
Трекер Keitaro и его база — только чтение: анализ и постановка задачи
владельцу вызывающего кода.
