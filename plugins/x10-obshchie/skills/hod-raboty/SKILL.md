# Ход работы

Основано на конвейере PRD → задачи → исполнение из `.cursor/rules`, но
подрезано под нас. Что именно выкинуто и почему — в конце, чтобы это не
восстановили обратно по недосмотру.

## Новый репозиторий — четыре файла, и больше ничего

Заводя репозиторий в организации, клади в него набор из
[`x10company/ci-guard/primer/`](https://github.com/x10company/ci-guard/tree/main/primer):

```bash
mkdir -p .github/workflows .claude
cp primer/guard.yml       .github/workflows/guard.yml
cp primer/settings.json   .claude/settings.json
cp primer/gitleaks.toml   .gitleaks.toml
cp primer/gitignore       .gitignore
```

| Файл | Что даёт |
|---|---|
| `.claude/settings.json` | своды правил подключаются при открытии репозитория |
| `.github/workflows/guard.yml` | восемь строк, зовущих общий проход CI |
| `.gitleaks.toml` | исключения поиска ключей, свои у каждого проекта |
| `.gitignore` | без него первый же коммит утащит `__pycache__` |

**Смысл правила: человеку, которому дали репозиторий, набирать не нужно
ничего.** Ни установки плагина, ни настройки проверок. Открыл — работает.

Команды вида `/plugin marketplace add` и `/plugin install` существуют, но это
запасной путь для того, кто работает вне подготовленного репозитория. Просить
коллегу их набрать — значит переложить на него то, что делается один раз
четырьмя `cp`. И забудется это ровно у того, кто нужнее всего.

Отдельно: то же касается **корня рабочей папки**, если репозиториев рядом
несколько. `settings.json` в нём подключает своды сразу для всех соседей.

**Почему `.gitignore` в списке, а не «само собой».** Первый пуш `ci-guard`
отклонила защита GitHub от секретов: `git add -A` в новом репозитории без
`.gitignore` утащил `__pycache__/*.pyc`. В исходнике строки были намеренно
склеены из кусков, чтобы сторож не ругался на собственный текст, — но
компилятор складывает константы, и в `.pyc` они лежат целиком.

## Когда заводить список задач

Не всегда. Порог — любой из трёх:

- работа не заканчивается за один заход;
- задевает больше одного каталога верхнего уровня;
- переживёт перерыв в разговоре (то есть контекст к ней придётся
  восстанавливать заново).

Разовая правка одного файла списка не требует. Заводить его на всё подряд —
бумажная работа ради бумажной работы.

Живёт список в `knowledge/org/`, рядом с остальными документами по устройству
монорепо, а не в отдельном `/tasks/`. Отдельный каталог под задачи у нас
превратился бы в третье место, куда надо не забывать заглядывать.

## Что выяснить до начала

Взято из `create-prd.md`, но подрезано: там это отдельный документ с
нумерацией и разделом «пользовательские истории». У нас это три вопроса,
на которые надо иметь ответ, — письменно или хотя бы вслух.

**1. Какую задачу это решает и для кого.** Не «что сделать», а «зачем».
Половина расхождений вылезает здесь: я понял «навести порядок в папке» как
переименовать, а имелось в виду выкинуть лишнее.

**2. Чего делать НЕ надо.** Самый полезный пункт из всего конвейера. Границу
проще проверить, чем содержание: «сервер не трогаем», «имена в каталоге
развёртывания не переименовываем», «историю git не переписываем». Записанная граница не даёт
работе расползтись, а расползается она незаметно — по одному разумному шагу
за раз.

**3. По чему поймём, что готово.** Не «сделано», а проверяемое: «семь задач
планировщика отработали с кодом 0», «страж краснеет на подложенном ключе и
чист без него». Если критерий нельзя запустить — он не критерий.

### Когда спрашивать, а когда решать самому

Спрашивать стоит **до** начала и только там, где разные ответы ведут к разной
работе. Если вариантов немного — перечислить их списком, чтобы можно было
ответить одной цифрой.

Не спрашивать: «продолжать ли», «делать ли следующий шаг», «правильно ли я
понял» там, где ответ очевиден из уже сказанного. План согласован — следующий
шаг очевиден — делать и докладывать.

Из исходных правил не берём и правило «не приступай к работе, пока не
утверждён документ»: у нас документ заводится только на крупное (см. порог
выше), а на остальное он был бы бумажной работой ради бумажной работы.

## Сначала осмотреться

До первой строчки плана — понять, что уже есть. Для этого репозитория это
означает конкретное:

```bash
python tools/kto-zovyot.py <ИмяТого-ЧтоТрогаем>   # кто это зовёт и из какого рантайма
ls <каталог>/README.md                             # чем этот каталог занят
git log --oneline -8 -- <каталог>                  # что там недавно делали
```

Смысл в том, чтобы план опирался на существующие соглашения, а не изобретал
рядом свои. Но и не связывал руки: если соглашение плохое, это повод сказать
об этом вслух, а не молча его повторить.

## Формат списка

```markdown
## Затронутые файлы

- `service/Controllers/Foo.cs` — обслуживает адрес /api/Foo, меняем имя маршрута
- `scripts/foo/script.js` — зовёт этот адрес снаружи, из другого рантайма
- `tools/check-secrets.py` — добавляем проверку, что адрес существует

## Задачи

- [ ] 1.0 Крупная задача
  - [ ] 1.1 Подзадача
  - [ ] 1.2 Подзадача
- [ ] 2.0 Крупная задача (без подзадач, если она чисто структурная)
```

Крупных задач обычно около пяти. Раздел «Затронутые файлы» — не украшение:
это единственное место, где записано, *почему* файл в этой работе участвует.
Через полгода имя файла об этом не напомнит.

Список живой. Всплыло новое — дописать, а не держать в голове.

## Сдача на независимую проверку

Крупную работу отдаём тестировщику — отдельному чату, который смотрит свежим
взглядом. Реестр помощников и их постоянные суффиксы держим в документе
проекта; находить через `ListAgents`, писать через `SendMessage`.

**Его выводы не принимать безоговорочно.**

- Согласен на все сто, без единого сомнения → принимаю и делаю.
- Сомневаюсь хоть в чём-то → **возражаю по существу и довожу с ним до полного
  согласия**, только потом делаю.
- Считаю неправым → говорю прямо, с доказательством.

Он для того и заведён, чтобы был спор, а не второй одобряющий голос. Ошибается
он так же, как я: не видит контекста, принимает намеренное решение за
недосмотр, предлагает то, что уже пробовали. Молча согласиться с тем, чего не
понял, хуже, чем не спрашивать вовсе: переделаешь работающее и внесёшь ошибку.

**Задание давать документом, а не пересказом в сообщении.** Проверяющий тоже
переживает сжатие контекста, и то, что не записано в файл, после сжатия не
существует. В документе: что сделано и зачем, какие решения отвергнуты и
почему, чем проверено с командами и выводом, **где сомневаюсь сам** и **чего
проверять не надо**. Последние два пункта важнее первых — они показывают, где
искать по-настоящему.

Итог разногласия записывать всегда: договорились — в свод или в документ
состояния, не договорились — в отдельный список спорного. Иначе тот же спор
повторится через месяц, и оба будут помнить его по-разному.

## Приёмка крупной задачи

Когда все подзадачи под ней отмечены:

1. **Прогнать проверки.** У нас это не `npm test`, а:
   ```bash
   python tools/check-secrets.py
   dotnet build api/                 # если трогали апишку
   ```
   Плюс главное: **запустить то, что починил**. Сборка и `py_compile` уже
   дважды пропускали ошибку, падавшую при запуске (см. свод `proverki`).
2. **Убрать временное.** Файлы-пробники, отладочный вывод, `.bak`.
3. **Добавить в коммит поимённо.** `git add -A` дважды заметал чужую
   незаконченную работу.
4. **Коммит** — conventional, несколькими `-m`:
   ```
   git commit -m "refactor: переименовать контроллер Foo в Bar" \
              -m "- поправлен маршрут в 3 вызывающих скриптах" \
              -m "- добавлена проверка существования адреса"
   ```
5. Отметить крупную задачу `[x]`.

## Что записывать, а что нет

Три правила из внешнего набора `personal-operating-system`. Сами его скиллы нам
не подошли — они пишут в свои каталоги и конфликтовали бы с уже работающей
памятью, — но эти три описывают ошибки, которые мы здесь уже сделали.

**Прочитай словарь целиком, прежде чем заводить новое имя.** Грепом смысловых
пересечений не видно: ищешь `PACHCA`, не находишь и заводишь своё, а рядом уже
сложилась схема с другим окончанием. Мы так потеряли время на очередном
секрете.
Словари у каждого проекта свои — реестр имён и реестр переменных. Читать
целиком, а не искать по подстроке.

**Не писать молча.** Записал в память или в документ — покажи что именно.
Незаметная запись хуже отсутствующей: её никто не проверит, а опираться на неё
будут. То же касается удаления: не стирать прежнюю запись, а заменять её новой
с объяснением, почему прежняя больше не верна.

**Факт, верный через год, стоит записи. Факт, истекающий через неделю, — нет.**
Именно поэтому пятнадцать наших документов разошлись с деревом: в них записаны
эпизоды, а не устройство. «Вчера выложили апишку» — эпизод, забудется сам.
«Имя класса контроллера задаёт боевой адрес» — устройство, будет верно и через
год. Первое пишем в `STATUS.md` и вычёркиваем, второе — в README раздела.

## Кто читатель

Не «джуниор-разработчик» из исходных правил, а **я сам через полгода** и
коллеги, которые в этот код не заглядывали. Отсюда
язык: русский, без жаргона, с объяснением *зачем*, а не только *что*.

## Что выкинуто из исходных правил и почему

- **«Останавливайся после каждой подзадачи и жди разрешения».** Прямо
  противоречит указанию не переспрашивать: план согласован — следующий шаг
  очевиден — делать и докладывать. Останавливаться стоит на другом: когда
  развилка меняет объём работы или когда шаг необратим.
- **Пауза «Go» между крупными задачами и подзадачами.** По той же причине.
- **Нумерация PRD `0001-prd-...` и каталог `/tasks/`.** Церемония под другой
  масштаб. У нас документы по устройству лежат в `knowledge/org/` под
  говорящими именами.
- **Тесты рядом с кодом (`*.test.ts`).** У нас почти нет юнит-тестов, и
  заводить их ради формы нет смысла. Заменено на «запустить то, что починил»,
  и на проверки в CI.

## Доставлять целиком, а не по одному файлу

Обновление, разосланное частично, ломает то, чего целое не ломает. Половина
новой версии встречается с половиной старой — сочетание, которого не было ни у
кого и которое поэтому никем не проверялось.

04.09.2026, замер на смоделированной машине пользователя:

```
старый запускающий файл + новый скрипт  → отказ у всех, кто уже установлен
установщик целиком                      → оба файла обновлены, отказа нет
```

Новый скрипт требовал переменной, которую выставлял только новый запускающий
файл. Доставка одного скрипта оставляла у людей старый запускающий — и всё
вставало, с сообщением, по которому ничего не понять.

**Правило: доставка только полным установщиком, никогда одним файлом.** Соблазн
«дошлю только изменившийся скрипт» возникает каждый раз: он быстрее, меньше и
выглядит безопаснее. Он и опаснее всего — именно потому, что сочетание версий
получается новое.

Проверять надо не на чистой машине, а **на машине с предыдущей версией**:
чистая установка проходит всегда, ломается обновление.

## Соразмерность круга проверки

Если проверка несколько кругов подряд находит одну и ту же поломку в новой
форме — остановиться и посмотреть, какая линия защиты держит задачу на самом
деле.

04.09.2026 семь кругов за час ушло на шаблоны поиска секрета: каждая находка
была настоящей, но задача «ключ не уедет в репозиторий» была закрыта первым же
круговым решением — сборщик отказывался писать внутрь репозитория, а gitleaks
стоял в CI. Шаблоны были третьей линией, а полировались как первая.

**Перечисление форм неполно по природе.** Пока защита строится списком того, что
запрещено, круги не кончатся: следующая форма найдётся всегда. Круговое решение
— то, после которого форма перестаёт иметь значение, — закрывает задачу за один
раз.
