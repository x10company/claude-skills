# Оболочка, кодировки и git

Всё здесь портит файлы **молча**: синтаксис остаётся верным, проверки проходят,
а ломается при запуске или у другого человека.

## Ты работаешь не один

**Над этим кодом работают другие люди, с других машин, прямо сейчас.** Это не
оговорка в конце, а исходное условие: почти всё в этом своде — следствия
именно из него.

Что из этого следует, и каждое уже случалось:

- **Незапушенный коммит не существует.** Пока он лежит у тебя, коллега берёт
  с сервера последнее, что там есть, — и собирает прод из устаревшего.
- **`git add -A` утащит чужую незаконченную работу.** Соседние сессии идут
  параллельно; файл, правленный десять минут назад, скорее всего ещё в работе.
- **Изменённые файлы в дереве могут быть не твои.** Перед коммитом смотри
  `git diff --cached --name-only` и сверяй со своим списком.
- **`git reset --hard` выбрасывает не только твоё** — и не различает «убрать
  коммит» и «выбросить работу».
- **Архивация или перенос репозитория ломает чужой конвейер.** Прежде чем
  трогать — выясни, **кто ещё из него собирает и выкладывает**. Человек
  узнает об этом в момент, когда ему нужно срочно выложить.

**Общее правило: перед действием, которое видят другие — пуш, архивация,
переименование, force, перенос — выясни, кого оно заденет.** Проверять надо
не «мой ли это код», а «кто ещё им пользуется».

Сегодня из-за нарушения этого правила прод падал дважды: сначала потому, что
заархивированный репозиторий оставил коллегу без конвейера, потом потому, что
он собрал версию восьмидневной давности — более свежей на сервере не было.

## Незакавыченный heredoc съедает обратные слэши

Обожглись семь раз за один заход. Худший случай: `\b` в регулярном выражении
стало управляющим символом `0x08`, и gitleaks начал давать 52 срабатывания
вместо 24 — без единого сообщения об ошибке.

Второй по неприятности: `"\n"` в шаблоне превратилось в настоящий перенос
строки, из-за чего замена «не нашла» нужный кусок, а скрипт сообщил об этом как
о нормальном исходе.

**Что делать:**

- писать `<<'EOF'` в кавычках — тогда оболочка содержимое не трогает;
- лучше складывать скрипт файлом и запускать файл;
- отдельный слэш собирать через `chr(92)`, а перенос через `chr(10)`;
- если якорь для замены содержит слэш — выбрать другой якорь, без него.

И общее правило: **проверять результат до записи, а не после**. У нас скрипт
записал сломанный файл, а `ast.parse` поймал это следующей строкой — файл уже
лежал на диске битым.

## Python на Windows пишет `\r\n`

Без `newline=''` в `io.open(..., "w")` получается `\r\r\n`. Так мы испортили 88
файлов, 22 513 вхождений, и удвоили номера строк в сообщениях компилятора —
из-за чего диагностика встала, пока не сравнили байты.

Коварство в том, что обычная проверка «CRLF или LF» к удвоенному CR **слепа**:
`b.count(b'\r\n')` считает его как обычный CRLF. Проверять надо на `\r\r\n`
отдельно.

И то же самое умеет делать сам git: файл, закоммиченный с CRLF, под атрибутом
`text eol=crlf` приезжает на Linux с `\r\r\n`. То есть порча может появиться
при выкачке, а не при записи.

## `bash -s` по SSH: чужая команда съедает stdin

Скрипт передан на вход по SSH, внутри вызывается программа, которая тоже читает
stdin, — и остаток скрипта молча обрезается. Пропавшая секция потом читается как
«проверка прошла, ничего не нашла».

Спасает `< /dev/null` у каждой такой команды.

## Правка боевого скрипта — только через переименование

Bash читает скрипт по мере исполнения. Правка на месте у идущего процесса
сбивает смещения, и он начинает выполнять обрывки строк. Класть новую версию
рядом и заменять одним `mv`.

Для PowerShell то же по духу: копировать во временное имя и переименовывать,
чтобы замена была одним шагом, а не «файл наполовину записан».

## Правку — сразу в коммит, коммит — сразу на сервер

**Незапушенный коммит не существует ни для кого, кроме тебя.** Если над кодом
работает не один человек, второй соберёт и выложит свою версию — и разойдутся
не файлы, а то, что крутится в бою.

Случай, ради которого это здесь. Работа шла ежедневно неделю, всё аккуратно
коммитилось — **96 коммитов**, и ни один не был отправлен. Последний пуш
оказался восьмидневной давности. Никто этого не заметил: локально всё зелено,
`git status` чист, история на месте.

Тем временем коллега взял последнюю версию **с сервера** — восьмидневной
давности, — доработал её у себя и выложил на боевой. Теперь на проде код,
которого нет ни в одной ветке, а месяц работы лежит в одном экземпляре на
одной машине.

**Правило:** закончил правку — коммит. Закончил задачу — пуш. Не «в конце дня»
и не «когда накопится»: между коммитом и пушем не должно быть работы.

**Чем ловить.** `git status` про это молчит — он показывает рабочее дерево, а
не отставание от сервера. Спрашивать надо явно:

```bash
git rev-list --count @{u}..HEAD    # сколько коммитов не уехало
git log --oneline @{u}..HEAD       # какие именно
```

Ноль — значит на сервере то же, что у тебя. Всё остальное — расхождение,
которое растёт молча. Лучше вынести это в автоматическую проверку: у нас она
теперь в `tools/proverit-svyazi.py` и роняет прогон, если счёт не ноль.

**Отдельно про чужой репозиторий.** Прежде чем архивировать репозиторий или
переносить код, выясни, **кто ещё из него собирает**. Архивация делает
репозиторий доступным только на чтение и ломает чужой конвейер выкладки — а
человек об этом узнает в момент, когда ему нужно срочно выложить.

## `git add -A` заметает чужую работу

Дважды подряд утащил в коммит чужие незавершённые правки; второй раз это уже
уехало в удалённый репозиторий.

Добавлять поимённо. Перед коммитом смотреть `git diff --cached --name-only` и
сверять со своим списком. Если в дереве есть чужие изменения — проверить, что в
индексе их нет:

```bash
git diff --cached --name-only | grep -E '<чужой каталог>' && echo ТРЕВОГА
```

Отдельный случай: если чужой файл отличается **только** починкой переносов
строк, это можно взять — но сначала доказать побайтово, что других изменений в
нём нет.

## Смешение латиницы и кириллицы в именах

`$plohо`, `sverено` — половина букв латинские, половина русские. И PowerShell, и
Python такие имена принимают, поэтому код работает, пока имя пишется одинаково.
Ломается при первой же правке в другом регистре раскладки, и глазами это не
видно.

Проверять поиском: имя, где есть и `[A-Za-z]`, и `[\u0400-\u04FF]`.

## Вывод внешних программ читается в кодировке системы

`subprocess.run(..., text=True)` берёт кодировку системы. `git` отдаёт UTF-8,
PowerShell — кодировку консоли. Мы получили и то и другое:

- путь с кириллицей от `git rev-parse` вернулся искажённым, обход нашёл ноль
  файлов, и проверка сообщила «чисто»;
- навязали UTF-8 вызову PowerShell — разбор упал, и проверка замолчала, сообщив
  об этом замечанием, которое не роняет прогон.

Задавать `encoding` явно и по источнику. Для PowerShell добавлять в команду
`[Console]::OutputEncoding=[Text.Encoding]::UTF8`.

## Пробел в пути ломает то, что незакавычено

Каталог с пробелом в имени (`Claude Code`, `Program Files`, `Cursor Projects`)
рвёт любую незакавыченную подстановку. Ошибка не в пробеле, а в кавычках,
которых нет, — и вылезает она только на той машине, где пробел есть.

Реальные случаи одного дня:

```bash
SBURL="file://$SB/..."      # curl: URL rejected: Malformed input
jq -s '.' $(cat parts.txt)  # каждое слово пути стало отдельным аргументом
for f in $spisok            # 5 записей из 9 молча не отслеживались
```

Третий — самый неприятный: сторож честно отработал и сказал «чисто», а половину
своего списка не видел вовсе.

Что делать:

- **Кавычить всё**: `"$peremennaya"`, `"$(komanda)"`, `jq -f "$FAYL"`.
- Списки читать не через `for f in $spisok`, а через `while IFS= read -r f`.
- В URL пробел кодировать: `"${put// /%20}"`.
- Массивы разворачивать как `"${massiv[@]}"`, не `${massiv[@]}`.

**Проверка одна: прогнать из каталога с пробелом в имени.** Проверка из
`/tmp/proba` зелёная всегда и не значит ничего — на этом уже обожглись: стенд
считался «не зависящим от расположения», потому что его ни разу не запускали
оттуда, где пробел есть.

## Одно и то же, установленное дважды, расходится молча

Средство от расхождения само его создаёт, если у него два места установки.

Плагин со сводами правил включался и на уровне машины, и ключом
`enabledPlugins` в настройках проекта — «чтобы открывший репозиторий получил
своды без команд». Через две недели на одной машине оказалось:

```
x10-obshchie  1.2.0  scope=user
x10-obshchie  1.0.0  scope=project   c:\Cursor Projects
x10-obshchie  1.1.0  scope=project   C:\Cursor Projects
```

Три копии трёх версий. Две последние — **один каталог, записанный с разным
регистром буквы диска**: для реестра установок это разные проекты, для файловой
системы Windows — один и тот же. Команда обновления двигала только уровень
пользователя и честно об этом писала («at user scope»), а проектные копии не
трогала никогда.

Проверять так:

```bash
claude plugin list          # больше одной строки на плагин — уже расхождение
```

**Правило: у общего ресурса одно место установки.** Проектный файл может
зарегистрировать источник, но не включать и не фиксировать версию. Если
инструмент позволяет поставить одно и то же в двух областях видимости — это
не удобство, а будущая расходящаяся пара.

И отдельно: **сравнивая пути, сравнивай их нормализованными.** Регистр диска,
прямой и обратный слэш, `~` против домашнего каталога — всё это даёт «разные»
пути к одному месту и множит сущности.
